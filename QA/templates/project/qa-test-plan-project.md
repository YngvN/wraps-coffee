## Methodology additions (project-specific)

*Numbered to continue after the base template's own 12 rules — a real plan should present these merged into one list, not as two separately-numbered sections, so a reader sees one continuous methodology.*

13. **What "fresh session" means mechanically, for this app.** "Fresh session" = calling the panel's own "New chat" button inside one continuously-running browser window — not relaunching Playwright/Chromium between scenarios. `localStorage`-backed settings (ingestion posture, per-chat model overrides, conversation log) are scoped to the browser profile, not the chat transcript, so they persist across "New chat" clicks. Confirm this is still true by re-reading `useLocalStorage`/`AssistantPanel`'s own state declarations if the assistant code has changed materially since the last run.
14. **Reuse `QA/scratchpad/qa/harness.mts` as-is before writing new scenario helpers.** See "Known harness state" below for what it already carries forward. Diff it against `QA/scratchpad 2/qa/harness.mts` (an older, pre-fix iCloud-sync-duplicate copy) if you're ever unsure which is current — the one under plain `QA/scratchpad/qa/` is authoritative.
15. **Known environment gotcha.** This repo lives under an iCloud-Drive-synced folder (`~/Desktop`) — heavy concurrent file writes into `QA/scratchpad/` during a long automated run can trigger iCloud to spin off a `"folder 2"` conflict-duplicate mid-run. This is sync noise, not data loss — don't panic-diagnose it as a script bug; verify by checking file mtimes and content before assuming anything broke.
16. **Concurrent-turn safety needs `sendChatConcurrent`, not `sendChat` twice in a row.** Every other scenario calls `sendChat` (or a helper built on it) once per turn and awaits full completion before the next call — Section E is the one deliberate exception. Use `sendChatConcurrent(page, message1, message2, { interrupt })` (`QA/scratchpad/qa/harness.mts`) for E.1–E.2, with `interrupt: 'cancel'` / `'newChat'` matching which affordance the scenario is testing. E.3 needs its own staging to actually reach the review gate first — drive it by hand with `clickGateTryAgain` rather than through `sendChatConcurrent`.
17. **Trace `checks[]` array.** Since the `server/assistant/postChecks/` framework landed (2026-08-04, commit `c5707c4`), every `AssistantTraceEntry` in the clipboard trace export can carry a `checks: [{name, ok, reason?, action?, attempt}]` array — read it directly for any Section K scenario instead of only inferring a check's verdict from screenshots or output text. A check `name` absent from the array for a step that should have run it is itself a finding (the check didn't fire at all), not the same as an `ok:true` verdict.

## Known harness state

*Not methodology rules — read this before writing a new harness helper, so a known fix isn't rediscovered from scratch.*

- `login()` calls `setDashboardLanguage(page, 'Norsk')` itself. A fresh browser context otherwise defaults to English, and every catalogue/category name this harness matches against (`AutoDeler`, `Dekk`, `Bremser`, ...) is Norwegian-only text with a blank English variant. Only call `setDashboardLanguage(page, 'English')` explicitly for the handful of scenarios that specifically test the English UI, then switch back.
- `sendChat`'s own trace capture reads the assistant panel's admin-only "Copy conversation to clipboard" export (`captureLatestTraceViaClipboard`) instead of clicking through every collapsible thought/step row in the DOM — faster and immune to expand/collapse timing. Each field is capped at 500 characters server-side. The old click-through version is kept as `captureLatestTraceDOM` for reference only — no current script should call it.
- `sendChat`'s own `reply` also captures the sibling `.assistant-list-attachment` element, not just the text bubble — a "list all products"/bilingual-filter-style reply's actual item list renders as a *sibling* of the bubble, not nested inside it.
- `productExistsInCategory(page, categoryName, productName)` expands the category section before checking — a raw item-count read on a still-collapsed section reads 0 even when the product is really there.
- `reachBatchReview(page)` checks for the Draft-Quality Gate first and clicks "Se detaljer" before checking for batch-review cards — checking `isBatchReviewVisible` directly, without opening a gate that might be sitting in front of it, produced a false `batch=false` reading across six scenarios in the qwen3:8b cycle even though the model had staged valid batches every time.
- `closeModelMenu(page)` waits for `.assistant-panel__transcript` to actually reappear after clicking the model menu's "back" button, not just for the click itself to resolve — `AssistantPanel.tsx`'s model-menu/transcript views are mutually exclusive under `AnimatePresence mode="wait"` with a 250ms exit animation, so returning immediately let the very next `newChat()` call's own `openAssistant()` open-check land mid-transition, read the transcript as absent, and click the sparkle toggle to "reopen" an already-open panel — which actually closed it. This raced on every other scenario in the multi-model cycle's own gemma3:4b run (2026-08-04), alternating real send-button timeouts with successful runs once the wrongly-closed panel got reopened correctly the next time around, before being caught and fixed mid-run.

## Known app-level findings

*Institutional knowledge about real bugs found (and fixed, unless noted) in this app — not methodology rules. Reproduce and cite when relevant, don't re-diagnose from scratch unless a run's own trace looks meaningfully different.*

- **Chat-driven update/delete via search previously stalled silently after correctly resolving the target item.** Corrected post-run (2026-08-03 cycle): the screenshots actually showed a real, working "Er dette den riktige?" confirmation prompt the test script never checked for or clicked — not a stall. A client-side fix (skip that confirmation tap when there's exactly one unambiguous candidate) was applied anyway, for parity with `create`. If a future cycle finds the confirmation prompt itself missing/broken, that's the regression to chase — see `useAssistantFlow.ts`'s `startOperation`.
- **Confirming one card in a multi-card batch review previously discarded the other, still-unconfirmed cards.** Root cause: an effect resetting the dismissed-gate flag was keyed on the whole `flow.state` object, so a same-status partial update re-triggered it. Fixed by narrowing the effect's dependency to `flow.state.status` alone (`AssistantPanel.tsx`). Re-verify by checking `batchCardCount` before/after a single-card confirm action.
- **A UI label was renamed from "Diettmerker" to "Kosthold-tagger"** (dietary-tags field, single-record review form) — any check written against the old label text will silently false-negative. Confirm the current label text directly from a screenshot before writing a new automated check against it.
- **Claude schema-union-count limit (fixed).** `fillFieldsSchema()` for an entity with too many nullable/`anyOf`-typed properties (>16) hits a real `400` from Claude's API ("Schemas contains too many parameters with union types"). `contactInfo` hit this before the fix (31 unions); fixed by de-nesting per-weekday nullability. If a future entity's schema creeps back over 16 unions as more fields get added, that's worth flagging explicitly.
- **Standing confabulation rule (confirmed three times):** a field whose valid values are grounded in live current-state context (what's currently hidden, a pane's current sizes, a monitor's current screen assignment) rather than a small, fixed, context-free enum is a confabulation risk on a local/weaker model — confirmed on `settings.hiddenSidebarItems`, `screen.textSizes`, and `displayManager.assignedScreenName`, all fixed via `AssistantEntity.confabulationRiskFields` (stripped from the schema under `'safe'`/local-default posture). Treat any new field matching that shape as confabulation-risk by default. The new `no-hallucinated-values-in-safe-mode` postCheck (Section K below) is a code-level belt-and-suspenders on top of this — see that check's own near-zero-expected-fire-rate caveat.
- **`AssistantEntity.destructive` and `.reviewComponent()` are both dead code** — never actually consulted by the real routing/rendering logic (confirmed by grepping the whole codebase). The real decision of whether a chat action shows the typed-confirmation destructive UI is hardcoded to a literal `action === 'delete'` check in `useAssistantFlow.ts` (`proceedWithItem`). Don't trust either field's presence as evidence a given action gets extra confirmation friction.
- **Local's generative verify-pass on `lookupQuery`/`answerLookup`/`selectItem` was removed 2026-08-04** (commit `c5707c4`, kept only for `lookupBatch`) in favor of the new deterministic `postChecks/` framework — see Section K. This is a real behavior change worth watching for regressions the narrower deterministic checks don't cover, not just a latency optimization to take for granted.

## Section K: Deterministic post-checks (standing scenario bank)

*Tests `server/assistant/postChecks/` (shipped 2026-08-04, commit `c5707c4`) — a code-level, deterministic auto-fix/reject-retry/reject-clarify layer that runs on parsed model output, replacing local's removed generative verify-pass on `lookupQuery`/`answerLookup`/`selectItem`. Pulled into a cycle's classification table whenever this framework or `server/assistant/postChecks/registry.ts`'s `CHECK_ENABLED` list has changed since the last cycle that covered it.*

*Design principle (learned the hard way — see the sharpening note this section's own history carries): a check that simply never fires during a cycle is not evidence it works. It's equally consistent with "nothing this cycle happened to trip it" and "the check is silently broken." So every check below gets its own adversarial row engineered to actually trigger it — a confirmed `ok:false` verdict (followed by the correct `auto-fix`/`reject-retry`/`reject-clarify` resolution) is the only thing that counts as a pass for that check on a first-ever cycle. A normal Section A/B/C scenario's own trace showing the same check firing `ok:true` cleanly is worth citing as the "doesn't false-positive on real input" half, but isn't a substitute for the adversarial half. Read every verdict from the trace's own `checks[]` array (Methodology #17) — don't infer from the reply text alone.*

*Exact phrasing below is a best-effort starting point, same posture as Sections E/F's own examples — a weak local model's own failure modes are inherently probabilistic, so refine at execution time against what the live model/data actually does, and note in the report when a row's first attempt didn't trigger its target check (retry once per the standing retry rule before concluding either way).*
