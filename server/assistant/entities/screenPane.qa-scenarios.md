# QA scenarios: `screenPane` entity

Pulled into a cycle's own classification table (see `QA/templates/project/qa-test-plan-project.md`) whenever `server/assistant/entities/screenPane.ts` or its client-side wiring (`AssistantPanel.tsx`'s own `screenPane` branch, `PaneCustomContentFields.tsx`, `src/utils/paneCustomCss.ts`/`paneCustomHtml.ts`) has changed since the last cycle that covered it.

**As of 2026-08-14, SP.1, SP.6, SP.7, SP.9, SP.10 and SP.18 have been exercised** (implementation session, local Ollama `qwen3:4b`/`qwen3:8b` only — Claude was not available, no API key configured in that environment). The rest are specified but not yet executed. Two real, load-bearing bugs were found and fixed by this initial pass — see "Findings from the 2026-08-14 session" below before re-running SP.9/SP.7 in a later cycle, so a regression there is recognized immediately rather than re-diagnosed from scratch.

## Findings from the 2026-08-14 session

1. **Candidate matching (fixed, see SP.9).** `listCandidates`' original needle-matching was a single literal `.includes(needle)` substring check against the auto-generated label format (`"Screen 2 — Pane 1 (catalogue)"`). A real `qwen3:4b`/`qwen3:8b` call produced `searchText: "Screen 2, Pane 1"` (comma, no content-kind suffix) — a perfectly reasonable paraphrase that failed the literal check outright, returning zero candidates before `selectItem` (`steps.ts`) ever got a chance to disambiguate. An intermediate per-word fix (every word present *anywhere* in the label) over-corrected the other way, matching unrelated panes purely because generic tokens like "2"/"1"/"pane" appeared scattered across a different screen's own stage-suffix. The shipped fix (`labelMatchesSearch`/`normalizeForMatch`) normalizes punctuation to spaces on both sides and requires the *whole normalized needle* as one contiguous run — tolerates separator drift while preserving word order/adjacency.
2. **`confabulationRiskFields` (fixed, see SP.7).** The entity's own doc comment stated `customCss`/`customHtml`/`applyToAllStages` "stay independently available even under `'safe'`, since none of them name a live-data-grounded value" — but the actual `confabulationRiskFields: ['customCss', 'customHtml', ...CONTENT_CONFABULATION_RISK_FIELDS]` array contradicted that, stripping all three under `'safe'` posture. This silently broke the styling-only path (the entity's *simplest*, always-offered capability) for any local-model session using the default `'auto'` posture, which resolves to `'safe'` for the local provider — confirmed via live testing: both `qwen3:4b` and `qwen3:8b` reliably left `customCss`/`customHtml` null across two different phrasings while filling only the two untouched trivial fields (`customHtmlPlacement`, `applyToAllStages`), a suspiciously consistent pattern that pointed at a schema-stripping bug rather than model noise. Fixed to `confabulationRiskFields: CONTENT_CONFABULATION_RISK_FIELDS` (`['content']` only), matching the doc comment's actual intent.

Both fixes are scoped to `screenPane.ts` alone — no other entity's matching/stripping behavior was touched.
