# QA scenarios: `screenPane` entity

Pulled into a cycle's own classification table (see `QA/templates/project/qa-test-plan-project.md`) whenever `server/assistant/entities/screenPane.ts` or its client-side wiring (`AssistantPanel.tsx`'s own `screenPane` branch, `PaneCustomContentFields.tsx`, `src/utils/paneCustomCss.ts`/`paneCustomHtml.ts`, `src/hooks/useScreens.ts`) has changed since the last cycle that covered it.

**As of 2026-08-14, all 19 original scenarios (SP.1-SP.19) have been exercised** across two sessions (implementation session + a full follow-up pass), local Ollama `qwen3:4b`/`qwen3:8b` only — Claude was not available, no API key configured in either environment. Four real, load-bearing bugs were found and fixed across the two sessions — see "Findings" below before re-running the regression-flagged rows in a later cycle, so a regression is recognized immediately rather than re-diagnosed from scratch.

**As of 2026-08-14 (second pass, same day), SP.1-SP.19 plus 41 of SP.20-SP.44's 25 rows have been exercised against `qwen3:4b` alone** — see `QA/Reports/assistant-qa-report-screenPane-qwen3-4b-2026-08-14.md` for the full report. **SP.12, SP.20, and SP.24 were not run this cycle** (deferred — need interactive human-draft-seeding/multi-tab automation not built in time). This pass found a new, load-bearing model-level bug (finding #5) that makes **SP.11 — a regression-flagged row — a FAIL**, via a different root cause than finding #4 below.

## Findings

1. **Candidate matching, round 1 (fixed, see SP.9).** `listCandidates`' original needle-matching was a single literal `.includes(needle)` substring check against the auto-generated label format (`"Screen 2 — Pane 1 (catalogue)"`). A real `qwen3:4b`/`qwen3:8b` call produced `searchText: "Screen 2, Pane 1"` (comma, no content-kind suffix) — a perfectly reasonable paraphrase that failed the literal check outright, returning zero candidates before `selectItem` (`steps.ts`) ever got a chance to disambiguate.
2. **`confabulationRiskFields` (fixed, see SP.7).** The entity's own doc comment stated `customCss`/`customHtml`/`applyToAllStages` "stay independently available even under `'safe'`, since none of them name a live-data-grounded value" — but the actual `confabulationRiskFields` array contradicted that, stripping all three under `'safe'` posture. Fixed to strip only `content`, matching the doc comment's actual intent.
3. **Candidate matching, round 2 (fixed, see SP.9).** The round-1 fix (whole-normalized-needle-as-one-contiguous-run) over-corrected in the *other* direction once real multi-word screen names entered the picture: needle "Screen 3, Pane 2" against the real label "Screen 3 (verify) — Pane 2 (image), Stage 1" needs "screen 3 pane 2" as one unbroken run, but the screen's own real name ("Screen 3 (verify)") inserts "verify" between "3" and "pane" — breaking contiguity across a boundary the model's own searchText never claimed to span, and returning zero candidates for a perfectly well-formed reference. Fixed by splitting the needle on its own comma boundaries (the model's own established convention) and requiring each segment to independently appear as its own contiguous run *anywhere* in the label — segments don't need to be adjacent to each other, but each segment's own words still do.
4. **`normalizeSlot` silently dropping fields on every normalization pass (fixed — the most serious finding of either session, see SP.11).** `src/hooks/useScreens.ts`'s `normalizeSlot` reconstructed a current-shape `ScreenSlot` from an explicit field list (`content`, `backgroundColor`, `backgroundImage`, `textSizes`, `language`, `locked`, `overflowMode`) instead of spreading the original value first — silently dropping every field added after that list was last written: `groupId`, `textColor`, and (this feature's own) `customCss`/`customHtml`/`customHtmlPlacement`/`customCssPolicyVersion`/`customHtmlPolicyVersion`. Since `useScreens()`'s own `useMemo` re-runs this normalization on *every* `screens` array change — client-wide, not just the pane being edited — a pane's already-confirmed `customCss`/`customHtml` would vanish from the client's own in-memory state the moment *anything else* touched `admin.screens`, and a subsequent save built from that now-stale state (`AssistantPanel.tsx`'s own `saveScreenPane`, but equally reachable from the human `ScreenForm.tsx`/`SlotEditor.tsx` path — this was never assistant-specific) would persist the loss back to the server, permanently erasing an already-valid value. Confirmed via a clean, isolated repro (two sequential styling turns each confirmed independently, then a third bundled styling+content turn) and fixed by spreading `...value` before overriding only the fields this branch actually processes — future-proof against the next field added too, not just today's.

5. **Short-form content-kind-switch phrasing frequently misroutes into `customCss`/`customHtml` instead of `content`, on `qwen3:4b` (not yet fixed — a model-prompting gap, not a code bug to patch directly, see SP.11/13/19/27/35).** A message shaped like "change the content to an announcement titled X" (no explicit "description" also named) produced a `fill_fields_screenPane` output with **no `content` key at all** in 6 of 8 observations during the 2026-08-14 qwen3:4b-only pass — instead writing the title as literal `customHtml` text (sometimes paired with an invented CSS block). Two of these were confirmed and applied to the real screens before being reverted in cleanup, one of them (SP.11) **live and undrafted** — the worst case, since content changes are supposed to always stage as a draft first. Not deterministic: the same phrasing shape succeeded correctly in SP.6 (title *and* description both named) and in one retry of the identical short "titled X" phrasing (SP.25). Suspected cause: the `content` schema branch is large (13 `kind` values, each with its own nested fields) — a smaller model may under-attend to it relative to the simpler, always-present `customCss`/`customHtml` fields on a terse instruction. Worth a schema/prompt restructuring pass aimed at making the `content` branch harder to skip past, and re-running SP.11/13/19/27/35 specifically once any such change lands.
6. **A new confabulation flavor on `content`'s live-data-grounded fields, distinct from finding covered by SP.14 (not yet guarded against, see SP.33).** Under `full` posture, `qwen3:4b` filled `locationId` with the *field's own JSON-schema description text*, verbatim, rather than a plausible fake id (SP.14's pattern) or `null` (the correct behavior). Both `no-hallucinated-values-in-safe-mode` and `input-mentioned-values-only` reported `ok:true` — this slipped past both existing postChecks. Worth adding a check for "value equals/closely resembles the field's own schema description" alongside the existing confabulation guards.

Findings 1 and 3 are scoped to `screenPane.ts` alone. Finding 4 is a shared-hook fix (`src/hooks/useScreens.ts`) — it affects the human admin editors too, not just the assistant, and was the real root cause behind what first looked like assistant-specific flakiness in SP.11. Findings 5 and 6 are both model-behavior gaps observed on `qwen3:4b` specifically, not (yet) code fixes — see the 2026-08-14 qwen3:4b report for full evidence.
