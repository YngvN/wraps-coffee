# ADHDisplay — Admin Dashboard & Kiosk Display

ADHDisplay is the owner-facing admin dashboard and fullscreen kiosk/digital-signage display system for a cafe — this repo ships pre-loaded with example content for a fictional cafe, Wraps & Coffee, serving wraps, baguettes, pizza, nacho plates, salads and a varied selection of coffee and drinks. The customer-facing marketing/ordering website is a separate project; this repo is just the owner's own tools: a login-gated dashboard for managing the menu, events, messages, orders and more, plus any number of fullscreen kiosk displays (`/screens/:screenId`) for extra monitors/TVs around the cafe.

Runs alongside an optional local server (`server/`) — a small Node/WebSocket process on the same network — that keeps every device (admin laptop, kiosk displays, a second admin's phone) in sync in real time, handles image/video uploads (transcoding any uploaded video into a browser-safe, compressed MP4), and can optionally bridge to a separate public website's own database (see "Website integration" below). With that server unreachable, the app still works from each device's own browser storage, just without cross-device sync.

## Features

- **Owner admin dashboard** (`/admin`, `src/features/admin`) — real login (seeded `admin`/`1234` on first boot; see "Authentication" below), a sticky sidebar nav, and:
  - **Overview** — stat tiles (revenue, orders, top sellers, customers).
  - **Messages** — inbox for contact-form submissions (local, or pulled from the public website — see "Website integration"), markable as read.
  - **Products** — organized as catalogues (e.g. "Food menu", a separate "Merch" catalogue for non-food items) → each catalogue's own categories → each category's own products, all admin-created/renamed/deleted (delete asks for confirmation) and drag-reorderable. Bilingual (English/Norwegian) name/description, an optional image on both categories and products, per-item or category-default pricing, an optional percentage- or amount-off discount (shown struck-through alongside the new price, highlighted on the item), allergen checkboxes, availability toggle.
  - **Events** — full CRUD for cafe events (recurring, postponed, cancelled occurrences; registration on/off).
  - **Contact info** — phone/email/address/opening hours.
  - **Appearance** (Settings → Store settings → Appearance) — create, edit and delete named color-palette + font themes for the screen displays, and pick which one is active store-wide. Every theme starts with 3 locked colors (white/black/grey) plus any number of custom ones, and 3 Google Font roles — body, heading, subheading — loaded automatically at runtime and applied across every slide type (menu, events, time, transit, news, and more).
  - **Orders** — online orders placed on the public website (pulled down live via the Neon bridge), merged with any Wolt/Foodora delivery orders in the same list (see "Delivery platform integrations" below); change status here and it reflects back on the website's own order-status page, or the matching delivery platform's own order.
  - **Screens** — the digital signage manager described below.
  - **Integrations** — enable/configure live-data screen-slot kinds: Ruter transit departures and a Yr weather forecast (both based on the cafe's address in Contact info), rotating RSS headlines from a fixed set of Norwegian news outlets, plus the Wolt/Foodora delivery-order integrations described below.
  - **Media library** (admin/subadmin only) — every image/video currently stored on the local server: an "+ Add" button or drag-and-drop to upload (a video transcodes into a browser-safe MP4 in the background, tracked by a live progress bar that keeps going even if you navigate elsewhere, plus a top-navbar upload indicator), rename, delete, retry a failed video transcode, a used/free storage summary, and a fullscreen lightbox (arrow-key or on-screen prev/next navigation) for reviewing an item full-size.
  - **Settings** — interface language, which sidebar items this cafe's dashboard shows, a "For developers" API reference page, and (admin/subadmin only) a **Printers** page for the receipt printers order boards print to (see "Receipt printing" below), and a "Testing" page for switching individual integrations between their own development and production environments (see below).
- **In-app updates** (Settings → App updates, `server/appUpdate/`, admin only) — pulls the newest version of the app straight from its GitHub repository and installs it, so shipping a change no longer means carrying the Windows installer to the kiosk. Checks what changed without downloading anything (the repo's file hashes are compared against the installed tree via the GitHub Trees API, so only genuinely changed files are fetched — a typical update moves a few hundred KB), shows the changed-file list and commit message before you commit to it, then builds the new version in a staging folder *beside* the install and only swaps it in once it has compiled — a broken commit fails harmlessly with the running app untouched. `server/data`, `server/uploads` and the installed fonts are carried across untouched, and the previous tree is kept on disk as a manual escape hatch. Needs a fine-grained GitHub access token (Contents: Read) entered on the page; the token is stored on the kiosk only and is never broadcast to any display. Startup scripts can't be replaced while the app is running, so an update that changes those says so and asks for the installer to be re-run.
- **AI assistant** (the sparkle icon in the admin top navbar, `src/features/admin/assistant`, `server/assistant`) — a chatbox that creates, updates, or deletes data across most of the dashboard from a plain-language request, in whichever language the admin's own dashboard is set to: products, catalogues, categories, events, non-admin user accounts, message boards and posts, appearance themes and theme colors, store branding, contact info, receipt printers, and integration on/off toggles. It never writes anything itself — every request only ever stages a draft, shown in the exact same form used elsewhere in the dashboard, and the admin has to explicitly confirm (typing the item's own name out, for a delete) before anything is actually saved or removed. When a request leaves a required field genuinely ambiguous (e.g. no category named for a new product), it asks a short multiple-choice clarifying question instead of guessing at one. It carries recent conversation context across turns, so a short follow-up like "remove the discount" resolves against what was just discussed — the faster/local tiers condense that context into a brief summary first, while Sonnet/Opus read the recent messages directly. Runs on either **Claude** (a cloud API key, entered on the Integrations page) or **Local** — a self-hosted, fully offline [Ollama](https://ollama.com) instance (Settings → AI Assistant to switch, Integrations page's Ollama card to configure the host and its two models), small enough by default to run on a Raspberry Pi (8GB RAM) alongside the local server, with bigger model tiers selectable for a more powerful machine — see `scripts/setup-ollama.sh`/`installer/linux/install.sh` below. Attaching a photo can also be used standalone, outside the create/update flow — pick "Just read this photo" to get a plain transcription of any photographed document (a menu, a price list, a house listing, anything), no draft or confirmation step involved. Beyond the model's own "double-check your answer" pass (tuned per step and per provider tier — skipped where it doesn't reliably improve on the first answer, kept where it does), a layer of deterministic, code-level checks (`server/assistant/postChecks/`) catches specific known failure patterns without ever making another AI call — a filter naming a field that doesn't exist, a "list all X" question that came back empty only because of an unnecessary filter, an ambiguous item picked with no real textual support, a fabricated allergen with nothing in the message backing it — auto-fixing what it safely can, retrying once, or asking a clarifying question instead of guessing; if a check still can't confirm a staged draft after that, the review screen shows a warning rather than silently trusting it.
- **Global search** (the magnifying-glass icon in the top navbar, `src/features/admin/search`) — one search box across almost everything in the dashboard: products, catalogues, categories, events, screens, every integration (including individual news sources), message boards/posts, users, settings pages, and every sidebar section. Results read as `<name> - <type or category>` (e.g. "Ruter# - Integration", "Kylling Fajitas - Wraps"); clicking one jumps straight to the exact editor for it — a product's edit form, an integration's own settings card auto-expanded and scrolled into view, an event's edit form — or, for the few things with no dedicated edit form (a user, a message board post, a news source), scrolls to and briefly highlights that row instead. Recently opened results are shown when the search box is empty.
- **Sidebar customization** (Settings → Sidebar items) — different cafes need different things; any section except Overview/Settings can be hidden from the sidebar entirely.
- **Screens (digital signage)** (`/screens/:screenId`, `src/features/screens` + `src/features/admin/screens`) — configure any number of fullscreen kiosk displays, each showing up to 4 independent content slots:
  - Per-slot content: a catalogue (pick which one, then which of its categories to show), one of several event views (an upcoming-events calendar list, a single upcoming event's own photo or details by ordinal position, or every event in the current month with optional price/description), a single centered image, a single video, a QR code (drawn in a single flat color matched to the pane's own contrast, no white background box) linking to either an admin-typed URL or a news source's own latest article — "Automatic" (the default) follows whichever headline a News pane elsewhere on the same screen is currently showing, or a specific source can be picked instead, either way with that source's own logo embedded in the code and the pane optionally themed to match, real-time transit departures (each line's mode icon sits inside its own colored line-number badge, with a choice of "Standard" or "Simple" mode-icon packs, and a badge's color prefers the line's own real official color from Ruter/Entur when it reports one, e.g. a Ruter regional bus rendering in its true green rather than the usual city-bus red), an hourly weather forecast (with a choice of "Outline" or "System" weather-icon packs), rotating RSS headlines from a chosen set of news sources (also themeable to the current headline's own source), a message board post, a short admin-authored announcement, or nothing — freely changed without ever losing a hidden slot's own settings.
  - **Video panes** — a video keeps playing uninterrupted through a stage transition, pane resize, or a pane's own identity changing underneath it (e.g. right after a split duplicates it into two panes at once, which then stay in sync with each other); per-pane options for muting/setting its volume, resizing its own pane to lock onto the video's aspect ratio (same "resize to fit" a single image already offers, draggable like any other pane border), advancing to the next stage automatically once it ends instead of looping, and restarting from 0 whenever the screen's stage rotation comes back around to stage 1. A display fully downloads a video (via the browser's own Cache API) ahead of when its stage actually needs it, rather than streaming it live each time.
  - Per-slot slideshow rotation on a shared, screen-wide timer, with a fade or slide transition; dragging a border or opening an editor pauses the rotation until "Play" is pressed again.
  - **Stage transitions** are choreographed in three steps rather than everything moving at once: the old content slides (or fades) out while the borders stay drawn around it, the borders then shrink away, the arrangement's new shape takes effect instantly while nothing distinguishable is on screen, and the borders grow back into their new positions before the new content arrives. A pane's background — colour and image alike — travels with the content it belongs to, so a sliding pane carries its own backdrop off with it instead of leaving it behind. Beyond reading as a deliberate sequence, this is also what keeps the geometry change from being *visible*: nothing high-contrast is moving at the moment the layout actually changes, and the change itself no longer animates, so a slow display has far fewer frames in which it can stutter.
  - An explicit "number of slots" (1-4) and on-screen arrangement, independent of whether each slot has content yet.
  - Text-size controls at every level, editable either live on the display itself or from the admin dashboard's tabbed screen editor.
  - A per-content **Padding** slider (scaling with the pane's own size) so a slot's content can be pulled in tighter or given more room to breathe — resets to that content kind's own default whenever the slot's content kind is switched, rather than carrying over.
  - Background color/image per screen and per slot (colors chosen from the store's active Appearance theme, see above), and shared borders with an adjustable color. A pane with no backdrop of its own is genuinely transparent, so the screen's own background shows straight through it — an image set screen-wide is drawn once behind the whole arrangement and reads as one continuous picture across every pane boundary, rather than each pane cropping its own slice of it.
  - If a slot's image can't be loaded at all, the pane falls back to the store's own logo (or, with no logo configured, a muted placeholder) instead of a broken-image icon — a blank pane on a kiosk nobody is standing next to is easy to miss entirely.
  - **In-place editing on a dedicated editor URL** — each screen has its own `/screens/editor/:screenId` link (the "Editor" button, next to "Open," in the admin Screens list) that, for a logged-in admin session, offers the same editing toolbar as the dashboard's own screen editor directly on the live display (resizing/splitting/clearing panes, dropping an image onto one, appearance controls). The plain `/screens/:screenId` URL real kiosk deployments use (opened via "Open") is always fully read-only, even from a logged-in device, so a live kiosk can never be accidentally edited. A **Live editing** toggle in the editor's toolbar switches between writing straight to the published screen (the default) and staging changes privately as a draft — invisible to every other viewer — until an explicit **Publish** makes them live everywhere.
  - **Screen saver** — a shared daily start/end window that any screen opted in to goes solid black during.
  - **Static preview thumbnails** — the admin Screens list shows each screen's own card as a static screenshot (one per stage, for a multi-stage screen, switchable via the card's own step arrows) rather than a live-rendered copy of the display, regenerated automatically whenever the screen is saved or published. This keeps the list itself cheap to render regardless of how many screens exist — no independent clocks, live data polling, video playback, or animations running per card — while the two dedicated editors (the dashboard's own form and the in-place editor above) stay fully live as before. A screen with no screenshot yet (or one still catching up right after a save) falls back to a live render for just that one card until its next save lands. The same stage-1 screenshots also back the ADHDisplay Companion's own remote-navigation browse mode below, cached on-device.
  - **Order boards** (`src/features/screens/orders`) — an "Orders" pane kind in two modes, each with a one-click template on the Screens page ("Create order board" / "Create pickup board"):
    - **Staff kanban** for a touch tablet running the Companion app: Innkommende → Lages → Ferdig columns (optionally split into Pickup and Wolt/Foodora Delivery lanes), large ← / → arrows on every card, a details view on tap, a 5-second undo after every move, and a History drawer of today's picked-up and cancelled orders with a way back to Done. Each card shows its items and total, how long ago it was placed (amber/red past configurable limits), overdue pickup times, and allergy-type notes in red; new orders chime and flash; a "To make" strip sums what's in progress; a clock sits top left. A ⚙ menu picks Light/Dark, the board's language and the printer, remembered per tablet. The board has its own fixed look, independent of the screen's theme. Moving an order is only accepted from a Display-Manager-approved device showing a staff board with "Touch control" on, one order at a time on the server (`server/orderStatus.ts`), and Wolt/Foodora orders are pushed to their platform first.
    - **Register** (`src/features/screens/register`, `server/register/`) — see "Register (counter tablet)" below; its own one-click template ("Create register") makes a full-screen register, separate from the kanban.
    - **Customer pickup board**, read-only: order numbers only (no names, phone numbers, items or prices) in "Lages nå" and "Ferdig" sections, two per row, Wolt/Foodora orders in their brand colour, a glide and pulse when an order becomes ready, and rows that shrink together to fit however long the queue gets. Follows the screen's own theme.
- **Display Manager** (Screens → Display Manager, `src/features/admin/displayManager`) — every kiosk machine, browser tab, or ADHDisplay Companion device that has registered itself as a display, and which Screen (if any) each of its monitors currently shows. A machine running the included Electron kiosk app (`electron/`, packaged via `installer/adhdisplay.iss` on Windows or `installer/linux/install.sh` on Linux) auto-registers every extra monitor it detects, skipping its own primary/admin display; a plain browser tab can register itself the same way at `/display-connect`; and the standalone **ADHDisplay Companion** app (`adhdisplay-companion/`, a separate Expo project with its own README) turns any Android tablet/TV box/stick, iOS/iPadOS device, or Windows/Linux PC into a kiosk display over the LAN, with no local server of its own. Windows and Android each get their own separate installer — a native APK for Android, built locally (`npm run build:tv` in `adhdisplay-companion/`) and embedded inside the main app's own `installer/adhdisplay.iss` at `{app}\android-apk\` for USB sideloading (see `installer/build-with-apk.ps1`), and a separate Electron-based kiosk shell for Windows built via its own `installer/adhdisplay-companion.iss`, produced by the `Build ADHDisplay Companion installers` CI workflow — see `adhdisplay-companion/README.md`; iOS and Linux packaging aren't built yet. A Companion device pairs once: after connecting to the server (auto-discovered via mDNS — showing the store's own name rather than a generic "ADHDisplay," with a selection list if more than one server answers on the same LAN — or entered manually), it shows up passively in Display Manager's own "Pending approval" section — no PIN or QR code to type or scan — and an admin approves it with one click, cross-checking the short `#suffix` shown on both the dashboard card and the device's own screen to tell several concurrently-pairing devices apart. A new pending request also surfaces in the top navbar's notification bell, linking straight to its card. After that it heartbeats in like any other display, can be revoked at any time by removing it here, and can also disconnect itself locally from the TV side (a plain button while unassigned, or a triple-Back-press gesture once a Screen is live) — which forgets its own server connection without revoking its Display Manager entry, letting it re-pair with the same server with no re-approval needed. Renaming a device here (its own name field) persists on the device itself, not just this server — so if it later connects to a different, previously-unseen server, it still shows up under the same name from the start.
  - **Update channel** — each Companion device reports its own app/JS-bundle version on every heartbeat, shown here as a per-device version/state badge (up to date, an OTA JS update available, a native APK update available, offline, or unknown for older builds that predate version reporting). Depending on how a device was provisioned, an update is pushed one of three ways: a silent OTA JS-bundle swap (self-hosted `expo-updates`, code-signed — see `adhdisplay-companion/codeSigning/CODE_SIGNING.md`) for any change that doesn't touch native code; a silent APK install with no on-screen prompt for a device set up as an Android device owner; or a same APK install with a user-confirmation prompt as the fallback for devices that aren't. Trigger a single device's update from its card, or roll an update out to every device at once via a staged bulk run (a few devices at a time, waiting for each batch to confirm before moving on, aborting the rest of the run if a device reports a failure); a rollback action reverts a device to its previous JS bundle.
  - **Remote screen navigation** — on a Companion device running on an Android TV, holding the D-pad up/down arms an on-screen browse mode that lets whoever is at the TV preview other Screens assigned to the same cafe directly with the remote, without touching the dashboard; stepping through Screens shows each one's own cached static screenshot rather than live-loading it, so browsing costs no page loads and no black frame, and pressing OK commits that Screen as a per-device override (shown here with an "Overridden" badge and a "Return to assigned" action) — only then does the display actually navigate to it. Back, 20 seconds of inactivity, or a lost connection all revert the preview with nothing committed. An override always takes precedence over Display Manager's own assignment for that device until explicitly cleared, and reassigning a Screen to that device here clears any active override.
  - **Max image resolution** — each device can be capped to a maximum image width, useful for an older or less powerful unit in a mixed fleet; its kiosk page then requests the largest pre-generated image variant that still fits under that cap instead of the full-resolution original. Left on **Automatic** by default, which instead picks purely from how large an image actually renders on that device.
- **Receipt printing** (Settings → Printers, `server/printers/`, `src/lib/receipt/`) — prints an order's receipt (store name, large order number, source, customer, phone, pickup and order time, every item with its price, notes in bold, total, and how a counter sale was paid) from the staff order board — a print button between the arrows on Done cards and in the details view — and from the register, after a sale (optionally automatically) or from its order history. Works with any ESC/POS receipt printer (Epson TM, Star, Bixolon, Xprinter and unbranded 58/80 mm printers), connected three ways: **on the network** (found by an mDNS browse plus a port-9100 scan of the local subnet, then printed to over raw TCP), **by USB to the server machine** (its print queues, printed raw through CUPS on macOS/Linux or the Windows spooler), or **by USB to a Companion tablet** (a native Android USB module, picked in that tablet's own ⚙ menu). Settings → Printers searches for printers, adds them by hand, sets paper width and the default, and makes test prints; a tablet's own printer choice falls back to the default if that printer is removed. Receipts print in Norwegian unless another language is chosen under Settings → Printers — the same language from every tablet, whatever its screen shows. Norwegian characters print via code page 865.
- **Register (counter tablet)** (`src/features/screens/register`, `server/register/`, `server/barcodes/`, `server/payments/`) — a "Register" pane for a touch tablet running the Companion app, on its own screen ("Create register" on the Screens page):
  - **Counter sales** — product tiles by catalogue and category, a cart with Takeaway / Eat in, an optional name to call out, and Pay. The server prices every sale from the live product list (the tablet never sends a price) and refuses it if a price changed meanwhile. A sale gets a daily counter number ("K12") and lands on the order board: straight to History when every item is "Handed over at the counter" (a product setting, e.g. a soda), otherwise in Incoming, with the ready-made items marked as already given. Sales reserve stock like website orders. Counter sales live in their own synced key and are never sent to the website.
  - **Finding products** — a search box above the tiles searches every catalogue by name (ignoring case and accents) or barcode, showing each match with its category; the tiles can be sorted by menu order, A–Å, or most popular (units sold over the last 30 days), remembered per tablet.
  - **Scanning** — a USB/Bluetooth keyboard-wedge scanner works anywhere on the page, or the tablet's own camera (Companion 0.3.11+) behind a **privacy switch**: off by default, a red "camera on" pill while it runs, released on screen change or when the app leaves the foreground, with an optional small aiming preview and a front/back switch. Every scan plays a sound (ok / needs a look / failed), which can be muted per tablet.
  - **Pickup QR codes** — scanning the QR on a customer's website order confirmation (or typing its code) hands that order over and moves it to History; an order that isn't ready yet asks first, a cancelled one is refused.
  - **Order numbers** (`src/lib/orderNumber.ts`) — every order has one 5-character number, shown on the pickup board, the staff board, receipts and history, whose first letter tells the source: a website order's number is its pickup code (`#K7M2Q`, never starting with F or W), Wolt orders start with W (`#W3F9A`), Foodora orders with F, and counter sales keep their daily number (`K12`).
  - **Barcode catalogue** — a scanned barcode is looked up in our own products first, then the server's own barcode catalogue, and only then on [Open Food Facts](https://world.openfoodfacts.org) (through the server, at most 10 lookups a minute). Every answer is saved server-side, misses for a week, so a barcode is looked up online at most once and works offline afterwards. A found product arrives as a draft (name with pack size, photo re-hosted with its CC BY-SA credit, allergens mapped only where they match exactly, the rest flagged) that staff confirm with a price; an unknown barcode opens a quick-add form. Nothing becomes sellable without a price. Products also get a barcode field (with "Look up") in the admin product editor.
  - **Staff lock** — adding or editing products at the register needs the staff PIN (Settings → Register), checked by the server, which keeps only a hash; an unlocked register locks itself after two idle minutes, and five wrong PINs lock a tablet out for five minutes.
  - **Payments** — until a payment integration is finished, staff take payment on their own terminal and record it ("Paid by card / cash / Vipps", with a change calculator for cash). Zettle (card reader) and Vipps MobilePay (QR) are scaffolded behind one payment interface, with credentials on the Integrations page and test-environment switches in Settings → Testing; neither takes real payments yet.
  - **Cash drawer** — a drawer plugged into a receipt printer's drawer port opens after every cash sale (once per sale) and from an "Åpne skuff" button that needs the staff PIN; no driver needed, since the printer opens it on command. Mark which printer has the drawer in Settings → Printers. Every opening is logged on the server with tablet, time and reason.
  - **Order history** — every order (counter, website, Wolt/Foodora), newest first by day, searchable by number, name or item, with a button to print any receipt again.
- **Personal-data retention** (`src/utils/orderRetention.ts`, `server/retention.ts`) — customer names, phone numbers and order notes are cleared from every order 7 days after it was placed (hourly, and whenever orders are pulled from the website). Sales history (items, totals, times, payment) stays. The public website clears its own copy daily.
- **Integrations** (`src/features/admin/integrations`, `server/integrations.ts`) — two live-data integrations derived from the cafe's address via the local server's `/integrations/*` proxy routes (Entur's geocoder + JourneyPlanner v3, and MET Norway's Locationforecast API): real-time bus/train departures from admin-chosen nearby stops, and an hourly weather forecast — each with an admin-configurable count/hours-ahead for what's actually *shown*, but always fetched/cached well beyond that (Entur's next 100 departures, MET's entire multi-day forecast) so a display has days' worth of buffer to keep drawing from if it goes offline, rather than running dry the moment whatever was on screen when the connection dropped has elapsed — see "Offline resilience" below. **Internet first, server as backup:** every display (including the Companion app) also fetches departures and the forecast straight from Entur and MET when it has internet access (`src/lib/entur.ts`, `src/lib/metForecast.ts`, the same fetch code the server uses), so it stays live even while the local server is down. For transit, the server keeps polling each stop (`server/transitPoller.ts`) and a display shows whichever of its own fetch and the server's snapshot is newer. For weather, a display asks MET first and the server second. Each integration has its own icon sets. A third, address-independent **News** integration (`server/news.ts`) lets the admin enable any of 7 seeded Norwegian outlets (NRK, VG, Aftenposten, Dagbladet, Nettavisen, Dagsavisen, Klar Tale); a News screen slot then rotates headlines from whichever of those are picked, and a QR code slot can link to one of those articles (see "Screens" above).
- **Delivery platform integrations** (the Wolt/Foodora cards on the Integrations page, `server/woltPoller.ts`/`server/woltAdapter.ts`, `server/foodoraPoller.ts`/`server/foodoraAdapter.ts`) — pulls delivery orders from Wolt's and Foodora's own POS Integration APIs into the same Orders view as website orders (each tagged with a small source badge), on a 30-second background poll plus a manual "Sync now," and pushes status changes made there back to whichever platform the order came from. Each platform's venue ID/API key is entered on its own Integrations card (admin/subadmin only); a "Use development environment" checkbox per platform (Settings → Testing) points its outbound calls at that platform's own sandbox host instead of production. Foodora's own base URL isn't confirmed yet — pending real partner API access — so only Wolt can reach a live endpoint today.
- **Website integration** (`server/neonBridge.ts`, `server/neonMappers.ts`) — an optional bridge to a separate public website's own Neon Postgres database: pushes admin-edited products, category prices, contact info and events up to it live (using that database's own `pg_notify` triggers plus a full reconciliation pass on every connect), and pulls contact messages and online orders back down into this dashboard. A developer API key, generated from Settings → For developers, is what the public website's own contact/order forms use to authenticate their submissions. See `NEON_DATABASE_URL` below to enable it.
- **For developers** (Settings → For developers) — reference documentation for the local server's own HTTP/WebSocket API (authentication, every synced data key, image/video uploads, the Integrations proxy, the delivery platform integrations, the Website integration), for anyone building a custom client against this cafe's own data.
- **Error notifications** — background/operational problems (e.g. the Website integration losing its connection) surface as a small box, top-right, across the whole admin dashboard; click it for the full detail.
- **Local LAN sync server** (`server/`) — optional Node/WebSocket process, run alongside the app: real multi-user login (`admin`/`subadmin`/`limited` roles, the latter scoped to specific dashboard sections), keeps every synced piece of admin data in sync across devices in real time, and handles image uploads with automatic WebP compression into several sizes (a tiny thumbnail up through a 1600px display-ready variant, plus a pre-blurred backdrop) — a kiosk display requests whichever size actually covers how large the image renders there, rather than always downloading the full-resolution original; a size missing for an image uploaded before it existed is generated on first request instead of falling back permanently. Also handles video uploads transcoded into a browser-safe MP4 with a poster frame. An uploaded file's stored URL records whichever address the *uploading* admin happened to reach the server on (`localhost`, a LAN IP, the `.local` name), so every device resolves such a URL against its own connection when rendering it — otherwise media uploaded from the server's own machine would silently fail to load on every kiosk display, since `localhost` there means the display itself.
- **Backup & storage cleanup** (Settings → Backup, `server/backup.ts`/`server/storageCleanup.ts`) — every synced key, user account, and uploaded image is continuously mirrored to a sibling `ADHDisplayBackup` folder; from here you can also download a point-in-time zip or restore from either that folder or an uploaded zip. **Storage cleanup** finds old orders/messages, expired message-board posts, display machines not seen in a while, and uploaded images no longer used anywhere — nothing is ever deleted automatically; you review the exact list and confirm before anything is removed.
- **Light / dark theme** that follows the OS preference by default, toggleable, and persisted.
- **Internationalization (i18n)** with English and Norwegian, easy to extend with more languages (`src/i18n`).
- **Offline resilience** via the PWA app-shell precache, so a kiosk display keeps working through a network drop — independent of, and unaffected by, the optional Website integration also being unreachable. The Ruter/Entur and Yr weather integrations additionally cache their own much-larger fetch buffer (see "Integrations" above) to `localStorage`, trimming past departures/hours off it as time passes, up to a week old — so transit and weather panes keep showing real (if increasingly dated) schedule/forecast data for as long as that buffer still has entries ahead of "now," instead of going blank shortly after the connection drops. A display that can still reach the internet doesn't need the local server for this at all (see "Internet first, server as backup" under Integrations); one that can reach only the server stays live from the server's data.

## Getting started

```sh
npm install
npm run dev      # start the Vite dev server + local sync server together
npm run build    # type-check and build for production
npm run preview  # preview the production build + local sync server together
npm run lint     # run eslint
```

The local server binds to all interfaces (`--host`), so it's reachable from other devices on the same network — open `http://<this machine's LAN IP>:5173` from a kiosk device or a second admin's phone. By default, screen links use the `.local` mDNS name (Settings → Advanced) instead of a raw IP, so they keep working across router/computer restarts. On Windows, this needs UDP port 5353 open for mDNS multicast — the Windows installer (`installer/adhdisplay.iss`) opens this automatically, alongside TCP 4000/4173 for the server itself, and — if the "Install Ollama" task is selected — installs Ollama itself from a copy bundled inside the installer (no network wait, and updated in place if it's outdated), together with the AI assistant's default text model (`qwen3:4b`, ~2.5 GB), pre-seeded into Ollama's own model store from a copy bundled in the same installer — so the assistant works offline the moment setup finishes, with nothing to download. Setup shows what Ollama and which models it found on the machine before installing anything, and skips the bundled copy if that model is already there. Only the vision model (`qwen2.5vl:3b`) is still downloaded later, on demand, from Settings → Integrations → Ollama. A machine running `npm run dev`/`npm run preview` directly will need that port allowed through Windows Firewall by hand the first time it's prompted. On Linux (e.g. a Raspberry Pi), `bash installer/linux/install.sh` is the equivalent turnkey setup: installs Node.js and Ollama, pulling the AI assistant's two default local models automatically as part of that same step (unlike Windows, see above), builds the app, opens the same ports via `ufw` if present, and registers a systemd service so it survives a reboot.

Ollama, specifically (for the AI assistant's Local provider), can also be set up on its own — without the rest of the installer — via `bash scripts/setup-ollama.sh`, e.g. to add it to an existing install or change which models are pulled.

Receipt printers need nothing installed: add them in Settings → Printers. A network printer must be on the same local network as the server (the search covers the server's own /24 subnet); one on another subnet can be added by its IP address. A USB printer on a Companion tablet needs Companion 0.3.9 or later.

A register needs a Companion tablet approved in Display Manager and showing a register screen (Screens → "Create register"), plus a staff PIN (Settings → Register) before products can be edited there. Any USB or Bluetooth barcode scanner that types like a keyboard and ends with Enter works with no setup; camera scanning needs Companion 0.3.11 or later and asks for camera permission the first time it's switched on.

Environment variables (all optional — the app works with none of them set):

| Variable | Default | Purpose |
| --- | --- | --- |
| `WS_PORT` | `4000` | Port the local sync server listens on. |
| `WEATHER_USER_AGENT` | a generic string | Identifies this app to MET Norway's weather API — set to include a real contact email as a courtesy to them. Applies only to the server's own calls; displays fetching MET directly send their browser's user agent, which a browser can't override. |
| `OFF_USER_AGENT` | `ADHDisplay/<version> (+https://wrapstesting.netlify.app/)` | The User-Agent the server sends to Open Food Facts for barcode lookups. Their terms ask every app to identify itself with a way to reach its owner — change it if the café's public address changes. |
| `NEON_DATABASE_URL` | unset | Enables the Website integration (see above) — Neon's **unpooled** Postgres connection string. No tunnel or port-forwarding needed: the connection is entirely outbound, from this server to Neon's public endpoint. |

On first boot, the local server seeds one admin account (`admin` / `1234`) — change the password from the Users-management flow once you're set up.

## Known bugs

- **A pane's content sometimes still flashes/pulses on a pure resize** — a pane whose own content hasn't actually changed between two stages can occasionally replay its fade/slide transition anyway when only its *size* changes (e.g. a sibling pane's `resizeToFit` locking in, or a divider drag propagated forward across future stages via "keep for next steps too") — most visible as a brief background/video "pulse" instead of a smooth resize. `LayoutPane.tsx`'s crossfade (`useCrossfadeSlot`) is keyed on the resolved content's own value specifically to avoid this, but it isn't fully eliminated yet.
- **`resizeToFit` can leave dead space around the media in some arrangements** — an image/video pane's own aspect-ratio lock can only adjust an axis that actually has a divider governing it (see `paneResizableAxes` in `src/utils/screenLayout.ts`). A pane that spans the full height (or width) of the screen with nothing dividing that axis can only be resized along its *other* axis, so the media's own aspect ratio isn't always matched exactly — the pane's own background shows through as dead space on the unconstrained side.
- **Splitting panes can sometimes leave a shared border "locked" across a whole row/column** — after some sequences of splits, two or more panes' dividers can end up moving together (or simply refusing to move individually) instead of resizing just the one border being dragged, with no in-app way found yet to un-link them — deleting the affected panes and re-splitting from scratch is the only known workaround so far. Possibly related to `PaneCornerHandle`'s own "merged handle" behavior (`LayoutTree.tsx`), which deliberately moves two aligned dividers together once they coincide into a true "+" intersection, but this can turn up even where that doesn't look like the case.
- **Ctrl-z not working on everytihng in editor**
- **A dropped server connection isn't noticed on the Companion tablet** — with the sync server stopped for 16 seconds, neither the order board's "Not connected" banner nor the kiosk's own no-connection icon appeared on the Android tablet, so the page never learns the socket closed. Order moves and prints made meanwhile still fail safely ("Not saved" / "Printing failed"), but the board shows stale data without saying so. Not yet diagnosed (the release build has no WebView devtools).
